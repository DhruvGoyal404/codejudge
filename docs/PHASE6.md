### Decision: generators and reference solutions go private

- **Generators must be private.** They are deterministic (fixed seeds), and their comments name every edge case. Public generator + any correct solution = the exact hidden tests. Keeping tests private while publishing generators protects nothing.
- **Reference solutions go private too.** A public `ref.cpp` is a copy-paste AC for every problem: the solved/attempted badges and the history would mean nothing. Together with any generator (or a contestant's own inputs) they also reproduce expected outputs. `wrong.cpp` / `slow.cpp` are test fixtures that reveal the intended approach and the trap; they stay with the refs.
- **Samples stay public**, as `problems/<slug>/samples/NN.in|out` (byte-identical copies of the private `tests/NN.*` for the names listed in `samples:`).
- **Generic tooling stays public:** `scripts/make-tests.py` (it runs whatever `gen/` and `solutions/` it finds; it moves to operate on the private checkout).

Resulting layout:

```
codejudge (public)                       codejudge-problems (private)
problems/<slug>/problem.yaml             <slug>/tests/NN.in, NN.out   (all tests, samples included)
problems/<slug>/statement.md             <slug>/gen/…
problems/<slug>/samples/NN.in, NN.out    <slug>/solutions/ref.cpp, ref.py, wrong.cpp, slow.cpp
                                         (Phase 5.5: <slug>/validator.*)
```

### Loader change (`runner/internal/problem`)

- New `LoadSplit(publicDir, testsRoot)`; `Load(dir)` stays as the single-directory form (tests in `dir/tests`) for fixtures and the pre-split layout.
- Tests are read from `$CODEJUDGE_PROBLEMS_TESTS_DIR/<slug>/tests/` (this is the configurable PROBLEMS_TESTS_DIR, named like the existing `CODEJUDGE_PROBLEMS_DIR`). If the variable is unset, the loader falls back to `<problems>/<slug>/tests` so the current layout keeps working until the split.
- Samples are taken from the public `samples/` directory and must be **byte-identical** to the private `tests/NN.*` with the same name, otherwise the load fails (no drift between what users see and what is judged).

That is the acceptance check.
- Who needs the private dir: `judge-admin import` (content hash) and every worker (judging). The API never does (it never read tests).

- **Only Caddy publishes ports.** `backend` is `internal: true` (no gateway, no route out). The worker runs on the host because it needs the Docker socket, so it reaches Postgres and Valkey through **Unix sockets** bind-mounted under `/run/codejudge`. There is no TCP port, not even on loopback. `/run/codejudge` is `0750 root:codejudge` (created by tmpfiles), so only the worker's group can reach the sockets.
- **Passwords everywhere.** The official Postgres image defaults to `local all all trust`, which makes any socket user a superuser. `POSTGRES_INITDB_ARGS=--auth-local=scram-sha-256 --auth-host=scram-sha-256` makes socket connections need the password too. Valkey runs with `--requirepass`.
- **Memory budget (2 GiB t3.small).** The containers' hard limits add up to about 800 MiB. The rest covers the OS, dockerd/containerd, the worker (`MemoryMax=256M`) and one sandbox at a time (`JUDGE_CONCURRENCY=1`). Each sandbox container carries its own memory limit (the problem's limit, ≤ 256 MB for the current problems), plus the compile container. A 1–2 GB swap file on the host is recommended as a safety net. Sandbox containers set memory equal to memory-swap, so they can't use it.
- **Images and versions** follow the two-week rule. Caddy 2.11.6 and 2.11.7 were under 14 days old, so this uses 2.11.4; Node is 22.23.3. The API runs its TypeScript with tsx, now a runtime dependency, because Node's built-in type stripping can't run TypeScript parameter properties.
- **Logs:** json-file, 10 MB × 3 per container.

**Caddy behavior:**
- Automatic HTTPS for `$CODEJUDGE_DOMAIN` (production: `codejudge.dhruvgoyal.tech`, from SSM `/codejudge/prod/domain`; there is no default), ACME contact `$ACME_EMAIL`, and HTTP redirects to HTTPS.

- Hashed `/assets/*` files are cached as immutable for a year. A missing asset is a real **404**, not the SPA page, and error responses are `no-store`.

- Every response, errors included, gets HSTS, `nosniff`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy: same-origin` and a restrictive `Permissions-Policy`, with no `Server` header.

## 6a.3 API production settings and the page CSP

- **Production settings:** `TRUST_PROXY=1` (exactly one hop, Caddy), `PUBLIC_ORIGIN=https://codejudge.dhruvgoyal.tech`, and `NODE_ENV=production`. The last gives the `__Host-cj_session` and `__Host-cj_oauth` cookies, which are `Secure`, `HttpOnly`, `SameSite=Lax` and `Path=/` (Phase 5).
- **Startup checks.** The config now refuses to start in production without `TRUST_PROXY`, since otherwise all clients would share one per-IP bucket. It also refuses an http `PUBLIC_ORIGIN` and missing GitHub credentials (`api/test/config.test.ts`).
- **Two CSPs, because a CSP only protects the document it arrives with.** The API serves only JSON and SSE, so helmet sends `default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'` plus `X-Frame-Options: DENY`. The page's policy has to arrive with the HTML and with the worker scripts, which Caddy serves. It is defined once, in the Caddyfile's `(csp)` snippet, and applied to the SPA and to `/assets/*`.

The page policy is tested against the production build (`web/e2e-prod/csp.spec.ts`, run with `npx playwright test -c playwright.prod.config.ts`). The app, Monaco (loading, highlighting, editing, language switch, theme switch and its web worker), the profile and the login-error banner all run with **zero CSP violations** and no console errors.

| Directive | Value | Why |
|---|---|---|
| `default-src` | `'none'` | Deny by default; everything needed is listed below. |
| `script-src` | `'self'` | Only our bundled modules. No inline scripts and no `eval` (the build has no inline script, and Monaco needs no eval). |
| `style-src` | `'self' 'unsafe-inline'` | **Required by Monaco**, which injects `<style>` elements and `style=""` attributes at runtime. Without it the experiment showed `style-src-elem` and `style-src-attr` violations and an unstyled editor. Hashes can't cover runtime-generated styles. The risk is CSS injection only; scripts stay locked. |
| `img-src` | `'self' https://avatars.githubusercontent.com` | GitHub avatars. `data:` was not needed (experiment). |
| `font-src` | `'self'` | `data:` was not needed (experiment). |
| `connect-src` | `'self'` | fetch and SSE to `/api` only. |
| `worker-src` | `'self'` | Monaco's editor worker is a same-origin file; `blob:` was not needed (experiment). |
| `manifest-src` | `'self'` | |
| `base-uri` | `'none'` | No `<base>` hijacking. |
| `form-action` | `'self'` | No form posts elsewhere (login is a link). |
| `frame-ancestors` | `'none'` | No framing (clickjacking). |
| `object-src` | `'none'` | No plugins. |
| `require-trusted-types-for` | `'script'` | DOM-XSS sinks (`innerHTML`, script URLs, `new Worker(url)`) accept only Trusted Types. The worker URL now goes through our `codejudge-worker` policy, which accepts only same-origin `/assets/*.js` (or Vite's paths in dev). |
| `trusted-types` | `codejudge-worker defaultWorkerFactory diffEditorWidget diffReview domLineBreaksComputer editorViewLayer richScreenReaderContent standaloneColorizer tokenizeToString` | Exactly the policies the app creates, recorded at runtime; any other policy name is refused. In the experiment, allowing only ours broke Monaco. **Re-run the prod CSP test after any Monaco upgrade.** |
| `upgrade-insecure-requests` | | Defence in depth. |

**Experiments** (`CSP_EXPERIMENTS=1`; each tightens one thing on top of the served policy):
- `style-src` without `'unsafe-inline'` → violations.
- `trusted-types` without Monaco's names → editor broken.
- Earlier runs, before tightening, showed that removing `worker-src blob:`, `font-src data:` and `img-src data:` produced no violations, so they were removed.

Monaco is trimmed (no find widget, suggestions or context menu; Phase 4), so policies belonging to contributions it doesn't include aren't needed.

## 6a.4 Worker as a systemd service (gVisor by default)

Files: [`deploy/systemd/judge-worker.service`](../deploy/systemd/judge-worker.service), [`deploy/systemd/worker.env.example`](../deploy/systemd/worker.env.example), [`deploy/systemd/codejudge.tmpfiles.conf`](../deploy/systemd/codejudge.tmpfiles.conf).

**Why on the host:** the worker drives the Docker engine, which it reaches through `/run/docker.sock`. Running it in a container would mean mounting the socket into that container, which is the same trust with an extra layer. Membership in the `docker` group is root-equivalent, so the host should run nothing else.

**gVisor by default.** The sandbox gained `Options.Runtime`, which becomes `HostConfig.Runtime` for every container. The worker reads it from `JUDGE_RUNTIME` (the unit sets `runsc`), `judge-run` takes `--runtime`, and the integration suites take `JUDGE_TEST_RUNTIME`. If the runtime isn't registered with the engine, `sandbox.New` fails at startup ("container runtime "runsc" is not registered…", verified on this Docker Desktop, which has no runsc) instead of silently falling back to runc. Empty means the engine default, so dev on Docker Desktop is unchanged.

**The unit:**

| Setting | Value | Why |
|---|---|---|
| `User` / `Group` / `SupplementaryGroups` | `codejudge` / `codejudge` / `docker` | Unprivileged user; the docker group gives the socket. |
| `EnvironmentFile` | `/etc/codejudge/worker.env` (0640 root:codejudge) | DB and Valkey URLs over Unix sockets, problems dirs. |
| `Environment` | `JUDGE_RUNTIME=runsc`, `JUDGE_CONCURRENCY=1` | gVisor; one sandbox at a time on 2 GiB. |
| `Restart` / `RestartSec` | `always` / `5s` | Back after crashes or a DB outage, without hammering. |
| `StartLimitIntervalSec` / `StartLimitBurst` | `10min` / `10` | Don't flap forever. |
| `KillMode` / `KillSignal` | `mixed` / `SIGTERM` | SIGTERM to the worker (it stops reading and finishes in-flight submissions); SIGKILL to everything only at the timeout. |
| `TimeoutStopSec` | `45min` | Longer than the longest submission: compile (1m50s since Phase 5.6: Go's 60 s compile wall; 1m35s before)  plus a full batch of 50 tests at the 10 s maximum, including the transfer allowance for 64 MiB of input and 50 maximal result frames at 1 MiB/s (28m08s), 29m58s in total (Phase 5.5 + 5.6; was 30 min before the transfer allowance). **Asserted by `TestSystemdStopTimeoutCoversLongestSubmission`**, which reads the unit file. If it is ever exceeded, the pending entry is reclaimed by the next attempt and fencing keeps the result correct. |
| `MemoryMax` / `MemoryHigh` | `256M` / `192M` | The worker process itself. Sandbox containers have their own cgroups and limits, set by the sandbox package. |
| `TasksMax`, `LimitNOFILE`, `CPUWeight` | 256, 4096, 100 | |
| Hardening | `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `PrivateDevices`, kernel/cgroup/clock/hostname protection, `RestrictNamespaces`, `RestrictSUIDSGID`, `MemoryDenyWriteExecute`, `LockPersonality`, native syscalls only, `AF_UNIX/AF_INET/AF_INET6` only, empty capability sets, `UMask=0077`; writable only `/run/codejudge` and `/run/docker.sock` | The Docker socket is the one door it needs. |

**Host setup** (Phase 6b, written here so it's reviewed now):

```sh
useradd --system --home /opt/codejudge --shell /usr/sbin/nologin codejudge
usermod -aG docker codejudge
install -d -o root -g codejudge -m 0750 /etc/codejudge
install -m 0640 -g codejudge worker.env /etc/codejudge/worker.env
install -m 0644 deploy/systemd/codejudge.tmpfiles.conf /etc/tmpfiles.d/codejudge.conf && systemd-tmpfiles --create
install -m 0644 deploy/systemd/judge-worker.service /etc/systemd/system/

```

gVisor is installed by `runsc install`, which registers the `runsc` runtime in `/etc/docker/daemon.json`; then dockerd is restarted. CI does the same (6a.5).

**A CI bug found and fixed.** Run 1 reported the runsc job green although `go test` printed `FAIL`. GitHub's default shell has no `pipefail`, so `go test | tee` returned tee's status. All jobs now run under `pipefail`.

**On Linux with runc, the whole sandbox suite passes** (51 tests). That is the first time the sandbox has run on Linux; it was previously only exercised on Docker Desktop/WSL2.

**Under gVisor the sandbox is NOT ready.** Production must not run with `JUDGE_RUNTIME=runsc` until these are fixed:

1. **Seccomp isn't applied inside gVisor by default.** Run 1 registered runsc without `--oci-seccomp`; the runtime's flag annotations showed `oci-seccomp: "false"`. `TestSeccompActive` then saw `keyctl` succeed.
2. **With `--oci-seccomp`, every C++ compile fails** (CE with empty stderr, 22 tests). Under gVisor our profile blocks something g++/ld needs, while Python (no compile step) passes. The profile was written for runc on a host kernel and needs a gVisor-aware review.
3. **Cross-test state leaks** (`TestBatchCrossTestState/snoopipc.cpp`). SysV shm/msg/sem objects and a POSIX mqueue planted by test 1 were FOUND by tests 2 and 3. The cause is our own fail-open: `judge-exec` enumerates `/proc/sysvipc/*` and treats a missing table as "nothing to clean". gVisor implements SysV IPC but has no `/proc/sysvipc`, and keeps POSIX mqueues outside `/dev/mqueue`, so nothing is removed and the check passes. Under runc these tables exist and the reset works.
4. **Fork bomb** (`TestProcessLimit`): judge-exec produced no result frame (IE) instead of a contained run. The pids cgroup limits the sandbox's host threads, not guest processes, so gVisor needs its own process limit.

**Proposed fixes (need your approval; they change sandbox invariants):**
- **IPC:** make the reset fail closed. If SysV IPC works (an `IPC_PRIVATE` probe succeeds) but it can't be enumerated, end the batch. Better still, deny the SysV IPC and POSIX mqueue syscalls in the seccomp profile altogether: judged programs never need them, and that removes the channel under both runtimes.
- **Seccomp under gVisor:** run with `--oci-seccomp` and find the syscall(s) blocking g++ (an strace of the compile under runsc), then adjust the profile. gVisor itself is the main boundary there, but our profile should still apply.
- **Processes:** test gVisor's own task limit (or keep the pids limit plus a judge-exec-side `RLIMIT_NPROC`) until `TestProcessLimit` passes under both runtimes.

The runsc job is left failing on purpose: it is the gate for using gVisor in production.

## 6a.6 Nightly pg_dump to S3, and restore

Files: [`deploy/backup/pg-backup.sh`](../deploy/backup/pg-backup.sh), [`deploy/backup/pg-restore.sh`](../deploy/backup/pg-restore.sh), [`deploy/systemd/pg-backup.service`](../deploy/systemd/pg-backup.service) + [`.timer`](../deploy/systemd/pg-backup.timer) (03:30 UTC, `Persistent=true`, ±10 min), [`deploy/backup/backup.env.example`](../deploy/backup/backup.env.example).

**Backup (`pg-backup.sh`).** The script:
1. Runs `pg_dump` inside the postgres container, so the client is the same major version as the server and nothing extra is installed on the host. It uses custom format (`--format=custom --compress=6 --no-owner --no-privileges`).
2. Checks the archive with `pg_restore --list` and refuses to upload one with no table data.
3. Uploads to `$BACKUP_DEST` (`s3://bucket/prefix`) with `--sse AES256` and the dump's SHA-256 stored as object metadata.

Credentials come from the EC2 instance role, so no AWS keys are kept on disk. The bucket name is taken only from the environment. Retention is an S3 lifecycle rule on the prefix (for example, expire after 30 days), set up in Phase 6b. `file:///dir` is supported for local tests.

**Restore (`pg-restore.sh <url | latest> [--into-live]`).** The script:
1. Fetches the dump and checks its SHA-256 against the recorded value. A mismatch aborts.
2. By default, restores into a **new** database `codejudge_restore_<ts>` and prints row counts for the restored and live databases side by side. A backup can be verified at any time without touching production.
3. With `--into-live`, it drops and recreates the live database, after you type its name. Stop the API and the worker first.

Commands that don't read input get `</dev/null`; otherwise `docker compose exec -T` would swallow stdin, including the confirmation. That bug was caught by the test below.

**Tested locally against the dev compose stack** (`CODEJUDGE_COMPOSE="docker compose -p codejudge -f compose.yaml"`, `BACKUP_DEST=file:///tmp/cj-backups`):

| Check | Result |
|---|---|
| backup | 20 KB dump, 7 tables with data, sha256 recorded |
| restore → new DB | sha256 ok; row counts identical to live for all 7 tables (schema_migrations 6, problems 5, problem_samples 10, users 1, sessions 1, submissions 8, submission_tests 38) |
| corrupted dump (1 byte changed) | refused: "sha256 mismatch", exit 1, nothing restored |
| `--into-live` with the wrong name typed | aborted, nothing dropped |
| `--into-live` confirmed | live DB replaced; counts identical; the full API suite (85 tests) then passed against it |

The scratch databases were dropped afterwards. CI runs `shellcheck --severity=warning` on both scripts and `systemd-analyze verify` on the units. Two info-level notes are intentional: the single quotes make `$POSTGRES_*` expand inside the container.

## 6a.7 gVisor fixes (approved; each tested under runc and runsc)

### 1. System V IPC and POSIX mqueues are denied; the reset can't fail open

- **Seccomp:** the profile no longer allows `shmget shmat shmdt shmctl msgget msgsnd msgrcv msgctl semget semop semtimedop semctl ipc mq_open mq_unlink mq_timedsend mq_timedreceive mq_notify mq_getsetattr`. They fail with the profile's default error, EPERM. Judged programs never need them, and denying them removes the cross-test channel under every runtime.
- **judge-exec guard:** once per batch, before the first test, judge-exec probes `shmget(IPC_PRIVATE)`. EPERM or ENOSYS is the expected, blocked outcome. If the probe succeeds (a runtime that doesn't apply the profile), judge-exec removes the segment and requires `/proc/sysvipc/{shm,msg,sem}`; if they're missing, it sends an **error frame**, and the submission is IE rather than judged in a box that can't be cleaned. A missing table no longer quietly means "nothing to clean". The per-test `/dev/mqueue` wipe and the SysV cleanup stay in place.
- **Tests:**
  - Unit (fakes): a failing guard gives an error frame, no ready frame, and no test runs.
  - Integration: `TestBatchCrossTestState` now also requires that planting a POSIX mqueue and SysV shm/msg/sem fails with "Operation not permitted". Locally (runc) the whole sandbox suite passes; under runsc it is checked in CI once C++ compiles there (fix 2).

### 2. Seccomp under gVisor: a runtime-specific profile (`clone3`)

**What CI showed (diagnosed with strace and syscall probes, `release-20260921.0`):**

| | runc + profile | runsc `--oci-seccomp` + profile |
|---|---|---|
| `clone3` (rule `errnoRet: 38`) | ENOSYS | **EPERM** |
| any denied syscall with `defaultErrnoRet: 38` (tested on a copy) | ENOSYS | **EPERM** |
| `posix_spawn` / `pthread_create` | work (glibc falls back to `clone`) | **fail** |
| `fork`, `clone(CLONE_VM\|CLONE_VFORK)` | work | work |

Docker passes `errnoRet: 38` in the OCI spec, but gVisor's `--oci-seccomp` ignores **every** `errnoRet` and returns EPERM. glibc ≥ 2.34 uses `clone3` in `posix_spawn` and `pthread_create`, and falls back to `clone` only on ENOSYS. Under runsc, g++ therefore couldn't start `cc1plus` (every C++ submission became CE), and every multithreaded program (std::thread, Python threading, and in Phase 5.5 the JVM and Node) would fail.

**Fix, decided by the owner: a runtime-specific profile.**
- **runc:** `sandbox/seccomp/default.json`, unchanged. `clone3` returns ENOSYS, glibc falls back to `clone`, and the profile filters `clone`'s flags, so no namespace creation is possible.
- **runsc:** derived in memory (`gVisorProfile`). `clone3` is taken out of its ERRNO rule and allowed for both compile and run containers. A unit test checks that nothing else changes.

**Threat-model argument.** The base profile denies `clone3` because seccomp can't inspect its flags, which sit in a struct in memory; under runc an unfiltered `clone3` would reach the host kernel's namespace code. Under runsc, the program's `clone3` is handled by gVisor's Sentry, a user-space kernel, and never reaches the host kernel, which removes that reason. Capabilities stay dropped and no-new-privileges stays on.

**Tests (both runtimes):**
- `TestThreads` (std::thread and Python threading) passes.
- `TestClone3`: plain `clone3` returns ENOSYS under runc and succeeds under runsc. Namespace flags must fail under both.

**Accepted risk: namespace creation inside the Sentry.** Under runsc, an unprivileged `clone3` can create some namespaces that Linux would refuse or that Docker's argument filtering normally blocks. `CLONE_NEWPID` still fails with EPERM. User namespaces need no capability on Linux either; Docker stops them only by filtering `clone`/`unshare` arguments, which isn't possible for `clone3`. A related observation has been reported privately to gVisor; details are withheld here until it's handled.
- **Probed** (one CI iteration): no `runsc` flag disables user or mount namespaces (only `TESTONLY-unsafe-nonroot` and `rootless` come near, and neither does this). gVisor has no `/proc/sys/user`, so there's no `max_user_namespaces` sysctl to set, and an OCI annotation can only override an existing flag.
- **Why accepted:** these namespaces exist only inside the Sentry (gVisor's user-space kernel), never in the host kernel, so they widen only the Sentry surface a program can reach.
- **Remaining layers:** the strict seccomp profile, otherwise identical to runc's (no SysV IPC or mqueues, no `keyctl`, …); all capabilities dropped; no-new-privileges; no network; read-only root filesystem with no host mounts; memory, CPU, pids and `RLIMIT_NPROC` limits; a uid unique to each container; and the batch resets and fail-closed IPC guard.
- **Test:** `TestClone3` requires `CLONE_NEWPID` to fail under both runtimes and every namespace flag to fail under runc. Under runsc it records the `CLONE_NEWUSER` and `CLONE_NEWNS` results in the log ("ACCEPTED RISK"), so a change in gVisor's behaviour is visible.

Public upstream issue draft (errnoRet only): [docs/upstream/gvisor-errnoret-issue.md](upstream/gvisor-errnoret-issue.md). The namespace observation is a separate, private report for gVisor's security contact, and is kept out of this repository.

### 3. Process limits that keep judge-exec alive

**Findings:**
- **IE even under runc.** The container's pids cgroup (64) is shared by judge-exec and the program. A thread bomb filled it, judge-exec's Go runtime then couldn't create an OS thread, and judge-exec died, giving IE.
- **Under runsc it's worse.** The host pids cgroup counts gVisor's own tasks (Sentry threads and systrap stub processes per guest address space). A 32-process guest fork bomb already exceeded 64 host tasks and killed the sandbox.
- **Crashing multithreaded programs hung.** With `RLIMIT_CORE=0` and a host `core_pattern` that pipes to a helper (WSL2 here; apport or systemd-coredump on Ubuntu), the kernel still runs the dump. A crash with threads alive took seconds, ending as TLE instead of RE.

**Fix:**
- **`RLIMIT_NPROC`.** judge-exec `--nproc` sets it on the program; fork and clone fail with EAGAIN at the limit. It's 48 under runc and 32 under runsc, below the pids budget with headroom for judge-exec. The pids cgroup stays as the outer layer: 64 under runc, and 256 under runsc, because there it bounds gVisor's own tasks while the Sentry enforces the guest limit.
- **A uid per container (owner-approved).** Each container runs as its own unprivileged uid (= gid) instead of the shared 65534. `RLIMIT_NPROC` counts a uid's tasks host-wide (there's no user-namespace remapping), so a shared uid would let one submission's tasks count against another's. It remains non-root, with no capabilities and no-new-privileges.
  - **Range:** `[1 000 000 000, 1 001 000 000)`. That's above every default user range (`UID_MAX` 60000, nobody 65534) and above the default subordinate-id span (`SUB_UID_MIN` 100000 to `SUB_UID_MAX` 600100000 in `login.defs`), and below 2³¹. `sandbox.New` refuses to start if `/etc/passwd`, `/etc/group`, `/etc/subuid` or `/etc/subgid` on the host has anything inside it.
  - **Unique among live containers, not random.** The allocator never hands out a uid that this process holds, and skips every uid labelled (`judge.uid`) on an existing `judge.managed` container from any process. The container is then created under the name `judge-u<uid>`. Docker reserves container names atomically and uniquely per daemon, so a second container with the same uid can't even be created while the first exists, in any state. A name conflict (409) means another process holds that uid, so the allocator tries the next one.
  - **Tests:** 200 concurrent allocations are distinct (unit); exclusion, release and exhaustion (unit); the host-range check against sample `passwd`, `group`, `subuid` and `subgid` files (unit). Integration: two independent sandboxes run 6 containers each, and a watcher snapshots the daemon's containers every 20 ms; no snapshot may show a `judge.uid` twice, and more than 6 must run at once, so the allocations really were concurrent. A container squatting a uid's name, without its label, must make creation move on to another uid.

  The first design arbitrated after creating: of all containers carrying a uid, the oldest by creation time kept it. It failed twice in CI. First, list timestamps are whole seconds, so a same-second tie let two containers "win". Then, on 2026-10-15 under runsc, a container stamped earlier became visible to `ContainerList` only after the other process had already listed, found itself alone, and started. Both ran with the same uid. Timestamps can't order visibility, so arbitration now relies on Docker's atomic name reservation. The earlier test also compared wall-clock lifetimes measured inside two gVisor sandboxes; the host-side snapshot check replaces it.
- **`RLIMIT_CORE=1`** instead of 0. The kernel refuses pipe dumps at a limit of 1, and 1 byte is below any file dump's minimum.

**Tests (both runtimes):**
- An unhandled thread bomb ends in **RE** (the uncaught `std::system_error` aborts it), with judge-exec alive.
- A fork bomb that handles EAGAIN is OK, and its process count stays below the binding limit (runsc: 23 started).
- The same fork bomb twice in one batch: both OK, and the container keeps working.
- A segfault with threads alive is RE in under 1 s.

A program that handles hitting the limit and exits normally gets its normal verdict. One that ignores the failure and keeps looping is stopped by the CPU or wall limit (TLE). Either way judge-exec stays alive, so the result is never IE.
